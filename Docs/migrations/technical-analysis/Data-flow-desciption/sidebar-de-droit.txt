4. DIVIDENDS
------------

Bloc visible :

  Dividends
  Earnings retained
  Payout ratio
  More info

Route principale :

  GET /api/proxy/10/api/v1/dividends/?action_ticker={ticker}&page_size=100

Route complémentaire utilisée pour le calcul du payout :

  GET /api/proxy/10/api/v1/results/?action_ticker={ticker}&page_size=500

Preuve CDP observée :

  Route applicative :
    GET /api/proxy/10/api/v1/dividends?action_ticker=SICOR_CI&page_size=100
    HTTP 200, Content-Type application/json.

  Route API cible équivalente :
    GET /api/v1/dividends/?action_ticker=SICOR_CI&page_size=100
    HTTP 200, page_size 100, count 11 792, total_pages 118.

  La réponse inspectée contient les champs amount, pay_date, ex_date,
  declared_date, record_date, frequency, type et action_ticker.

Limite API constatée pendant cette preuve :

  La requête demandait action_ticker=SICOR_CI, mais les premières lignes
  observées contenaient action_ticker=FRONTIER_TRANSPORT. La réponse API
  ne prouve donc pas que le filtrage serveur par ticker est effectif.
  Ce n'est ni une donnée locale ni une autorisation de mélanger les titres :
  le contrat API doit filtrer correctement les lignes du ticker demandé,
  ou le transport doit les valider avant affichage. Cette limite doit rester
  visible jusqu'à correction et nouvelle preuve CDP.

Transport applicatif :

  dividend API
    → core/infra/store/api/dividend.api.ts
       endpoint getAllDividends, GET /dividends/
    → core/infra/repositories/dividend.repository.impl.ts
       getAllDividends({ action_ticker, page_size: 100 })
    → components/technical-analysis/components/sidebar/data/sidebarDataPortAdapter.ts
       fetchFundamentals()
    → useSidebarDataFeeds
    → useSidebarDerivedMetrics
    → buildDividendsChartOption()
    → DividendsPanel.tsx

Correspondance des données :

  DividendEntity.amount
    → BRVMDividendPoint.value
    → montant du dividende utilisé par le graphique et l'historique.

  DividendEntity.pay_date
    → BRVMDividendPoint.year
    → année affichée dans l'historique.

  DividendEntity.ex_date
    → BRVMDividendPoint.exDate
    → date ex-dividende de More info.

  DividendEntity.pay_date
    → BRVMDividendPoint.payDate
    → date de paiement de More info.

Calculs réellement appliqués en mode réel :

  1. Le dernier dividende valide est pris depuis la série Dividends API.
  2. Le rendement calculé est :
       (dernier dividende API / prix actuel API) × 100
  3. Si un bénéfice API de la même année est disponible :
       shares = capitalisation API / prix actuel API
       EPS = bénéfice net API / shares
       payout ratio = (dividende API / EPS) × 100
       puis clamp entre 0 et 100.
  4. La part « Earnings retained » du graphique est le complément :
       100 - payout ratio.
  5. Si le bénéfice correspondant est absent, le payout ratio n'est pas
     inventé. Le graphique peut afficher le rendement dividende API comme
     mesure de repli contrôlée ; ce rendement est alors mis à l'échelle
     pour le cadran et ne constitue pas un payout ratio API.
  6. Donnée API absente ou invalide → ratio N/A ou bloc indisponible.
     Aucun dividende, bénéfice ou ratio local ne complète le mode réel.

More info :

  Ouvre DividendHistoryModal avec la série déjà résolue par le flux API.
  Le modal affiche l'année, le montant, exDate et payDate ; il ne crée
  pas une seconde source financière.

Règle de provenance :

  Les montants et dates viennent de l'API Dividends.
  Earnings retained et Payout ratio sont des dérivations de présentation
  à partir de données API ; ce ne sont pas des champs bruts de la route.
  Le résultat API /results/ observé sur la surface actuelle peut être
  indisponible (HTTP 401) : dans ce cas le payout reste non vérifiable,
  sans fallback local.

Affichage :

Source des données :

  GET /api/proxy/10/api/v1/cours/?instrument={instrumentId}&page=1&page_size=100
  GET /api/proxy/10/api/v1/cours/?instrument={instrumentId}&page=2&page_size=100
  GET /api/proxy/10/api/v1/cours/?instrument={instrumentId}&page=3&page_size=100

Logique réelle :

  1. Les clôtures OHLCV API sont chargées dans chartData.
  2. Les années sont extraites des dates de chartData.
  3. Les années distinctes sont triées par ordre décroissant.
  4. Les trois années les plus récentes sont affichées.
  5. Pour chaque année, startPrice est la première clôture de l'année.
  6. Pour chaque clôture, le rendement est calculé ainsi :
       ((close - startPrice) / startPrice) × 100
  7. Les rendements sont associés aux mois correspondants.
  8. Sans nouvelle valeur pour un mois, la dernière valeur valide est conservée.
  9. Le graphique affiche les rendements mensuels cumulés en pourcentage.

Preuve de provenance :

  Les années sont dérivées localement des dates OHLCV API.
  La formule est calculée par le graphique à partir des clôtures API.
  Aucun champ seasonals explicite n'est consommé depuis l'API.
  More seasonals est une navigation UI vers la page détaillée.

Calcul local du score :

  RSI score =
    clamp((RSI14 - 30) × 2,5, 0, 100)

  Trend score =
    clamp(50 + ((SMA20 - SMA50) / SMA50) × 500, 0, 100)

  Price score =
    clamp(50 + ((Prix actuel - SMA20) / SMA20) × 1000, 0, 100)

  Score final =
    RSI score × 40%
    + Trend score × 30%
    + Price score × 30%

Conversion du score en sentiment :

  score < 25       → Strong sell
  25–44            → Sell
  45–54            → Neutral
  55–74            → Buy
  75–100           → Strong buy

Conversion du score en pourcentages du cadran :

  directionalScore = round(score × 2 - 100)
  hold = 100 - abs(directionalScore)

  Si directionalScore >= 0 :
    buy = directionalScore
    sell = 0

  Sinon :
    buy = 0
    sell = abs(directionalScore)

Conclusion :

  RSI14, SMA20 et SMA50 viennent de l’API.
  Le score, le sentiment et les pourcentages Buy/Hold/Sell sont des dérivations UI.
  Ils ne sont pas des recommandations brutes renvoyées par l’API.

11. HISTORICAL VOLATILITY CURVE (28 DAYS)
-----------------------------------------

Bloc visible :

  Historical volatility curve (28 days)
  Notice UI : Courbe calculée à partir des clôtures API

Source des données :

  GET /api/proxy/10/api/v1/cours/?instrument={instrumentId}&page=1&page_size=100
  GET /api/proxy/10/api/v1/cours/?instrument={instrumentId}&page=2&page_size=100
  GET /api/proxy/10/api/v1/cours/?instrument={instrumentId}&page=3&page_size=100
  GET /api/proxy/10/api/v1/cours/?instrument={instrumentId}&page={N}&page_size=100

Données API utilisées :

  CoursEntity.close
    → ChartDataPoint.close
    → closePrices transmis à buildVolatilityCurveOption()

Transport applicatif :

  Route API Cours
    → core/infra/store/api/cours.api.ts
       endpoint getAllCours, méthode GET /cours/
    → core/infra/repositories/cours.repository.impl.ts
       getCoursHistory({ instrument }, maxPoints)
    → components/technical-analysis/hooks/MarketData/useMarketData.ts
       getActionByTicker → action.instrument → getCoursHistory
    → lib/utils/marketDataTransform.ts
       coursEntityToChartDataPoint → coursSeriesToChartData
    → chartData du contexte Technical Analysis
    → useSidebarCharts.ts
    → sidebarVolatilityChartOptions.ts
       buildVolatilityCurveOption()
    → shared/utils/volatility-engine.ts
       getVolatilitySkew(closePrices, 28)
    → ECharts

Logique réellement appliquée :

  1. La fenêtre métier est de 28 jours.
  2. Le moteur exige actuellement prices.length >= window + 2 ; avec window=28,
     il faut donc au moins 30 clôtures pour produire une courbe non vide.
  3. Les dernières window + 1 clôtures sont retenues, soit 29 clôtures.
  4. Pour chaque paire de clôtures positives consécutives :
       logReturn = ln(close_t / close_t-1)
       squaredReturn = logReturn²
  5. Le domaine de prix est étendu de 10 % de chaque côté du min/max observé.
  6. Vingt-six points sont générés sur ce domaine (numPoints=25, bornes incluses).
  7. Pour chaque point x, le noyau gaussien est appliqué :
       u = (price - x) / h
       poids = exp(-0,5 × u²)
       h = range × 0,30
  8. La variance lissée est la moyenne pondérée des squaredReturn.
  9. La volatilité annualisée affichée est :
       sqrt(variance lissée × 252) × 100
  10. Prix et volatilité sont arrondis à deux décimales avant affichage.

Contrat UI et limite actuelle :

  Le hook active le renderer à partir de 28 points chartData, mais le moteur
  getVolatilitySkew() refuse encore 28 ou 29 clôtures et renvoie une série vide.
  Cette différence de seuil est une limite d'implémentation à surveiller ; elle
  ne doit pas être masquée par une donnée locale.

Règle de provenance :

  Ce graphique ne lit aucun champ de volatilité native de l'API Actions.
  Il dérive sa courbe exclusivement des clôtures OHLCV API déjà transportées
  dans chartData. Série vide, clôtures invalides ou historique insuffisant
  → courbe indisponible. Aucun prix, rendement ou niveau de volatilité local
  ne complète le mode réel.

HISTORIQUE UTILISÉ PAR LE GRAPHIQUE
--------------------------------------

Bloc concerné :

  Historique OHLCV utilisé par le graphique principal et les vues dérivées
  qui ont besoin de chartData.

Résolution de l'instrument :

  1. L'action du titre est résolue par la route API principale.
  2. Le champ action.instrument fournit {instrumentId}.
  3. Ce même identifiant est transmis à la route canonique Cours.
  4. Aucune URL historique locale ni dataset statique n'est utilisé en mode réel.

Route API et paramètres :

  GET /api/proxy/10/api/v1/cours/?instrument={instrumentId}&page=1&page_size=100
  GET /api/proxy/10/api/v1/cours/?instrument={instrumentId}&page=2&page_size=100
  GET /api/proxy/10/api/v1/cours/?instrument={instrumentId}&page=3&page_size=100
  GET /api/proxy/10/api/v1/cours/?instrument={instrumentId}&page={N}&page_size=100

  instrument :
    identifiant d'instrument fourni par l'action API ;
    paramètre obligatoire et validé avant l'appel.

  page_size :
    100 éléments par réponse API ;
    la valeur est définie dans getCoursHistory du repository.

  Fenêtre initiale :
    500 points maximum ;
    soit jusqu'à 5 pages de 100 éléments.

Données API utilisées :

  CoursEntity.timestamp          → ChartDataPoint.time
  CoursEntity.open               → ChartDataPoint.open
  CoursEntity.high               → ChartDataPoint.high
  CoursEntity.low                → ChartDataPoint.low
  CoursEntity.close              → ChartDataPoint.close
  CoursEntity.volume             → ChartDataPoint.volume
  CoursEntity.number_of_trades   → tradesCount / trades_count

Transport applicatif réel :

  Route API Cours
    → core/infra/store/api/cours.api.ts
       endpoint getAllCours, méthode GET /cours/
    → core/infra/repositories/cours.repository.impl.ts
       getCoursHistory({ instrument }, maxPoints)
    → components/technical-analysis/hooks/MarketData/useMarketData.ts
       getActionByTicker → action.instrument → getCoursHistory
    → lib/utils/marketDataTransform.ts
       coursEntityToChartDataPoint
       coursSeriesToChartData
    → chartData du contexte Technical Analysis
    → graphique principal et vues dérivées autorisées

Pagination réelle :

  1. La page 1 est toujours chargée en premier.
  2. Si total_pages est fourni par l'API, le repository charge les pages
     suivantes jusqu'à la limite maxPoints.
  3. Sinon, il suit links.next tant qu'une page suivante existe.
  4. Les pages sont fusionnées dans leur ordre de réponse.
  5. La série est triée par timestamp croissant dans
     coursSeriesToChartData.
  6. requestMoreHistory augmente la fenêtre par tranches de 500 points,
     jusqu'à une limite UI de 10 000 points.

Consommateurs :

  Données OHLCV/chartData :
    graphique principal en chandeliers ;
    volume et vues liées au graphique ;
    Seasonals, qui dérive ses années et ses rendements des clôtures API ;
    Historical volatility curve (28 days), qui dérive sa courbe des clôtures API ;
    autres indicateurs locaux explicitement documentés comme dérivés.

Séparation avec le graphique term structure :

  Historical volatility term structure ne lit pas cette série OHLCV en mode réel.
  Il consomme action.latest_technical_indicator.hv_10, hv_20, hv_30,
  hv_60, hv_90 et hv_252 depuis la route Actions.
  La courbe OHLCV « Historical volatility curve (28 days) » est une surface
  distincte et utilise chartData.

Règle de provenance :

  Mode réel :
    les bougies et champs OHLCV viennent de l'API Cours ;
    le tri chronologique est une normalisation de transport ;
    champ absent ou invalide → le normalizer applique uniquement ses garde-fous de forme ;
    série vide ou échec API → chartData vide ou état indisponible ;
    aucune donnée financière locale ne complète la série.

  Mode mock :
    aucun mock financier ne doit remplacer la source API en mode réel ;
    toute donnée de démonstration doit rester isolée du flux réel.

ERRATA RUNTIME — SYNCHRONISATION API-FIRST
-------------------------------------------

Cette section prévaut sur toute description antérieure d'une formule locale en mode réel.

RESULTS / REVENUS :

  Route :
    GET /api/proxy/10/api/v1/results/?action_ticker={ticker}&page_size=500

  Le proxy BFF récupère désormais le accessToken NextAuth côté serveur et le transmet
  à l'API distante sous la forme Authorization: Bearer <accessToken>. Le navigateur
  ne transporte ni ne lit directement le token.

  Si aucune session authentifiée n'est disponible, l'API peut encore répondre HTTP 401.
  Dans ce cas, les revenus restent N/D. Le frontend ne reprend aucune valeur de catalogue,
  de mock ou de cache financier pour masquer cette absence.

  Le HTTP 401 n'est donc pas traité comme une donnée vide valide : il signifie
  « données financières protégées non accessibles dans la session courante ».

DEVISE :

  La devise source du titre est exclusivement lue depuis
  action.bourse.currency.symbol.

  Si ce champ API est absent, la devise source reste vide et l'interface doit afficher
  N/D ou indisponible. Le provider ne remplace plus cette absence par XOF.

  XOF peut rester la préférence d'affichage initiale choisie par l'utilisateur dans
  le sélecteur de devise ; ce n'est pas une preuve de la devise native du titre.

BRANCHES D'EXECUTION :

  Mode réel :
    champs financiers API uniquement ; absence API → N/D/indisponible ;
    aucune formule locale de saisonnalité, recommandation, objectif, dividende ou
    volatilité ne complète les données.

  Mode mock :
    les calculateurs locaux peuvent produire des valeurs de démonstration isolées ;
    ces valeurs ne doivent jamais être injectées dans le mode réel.
